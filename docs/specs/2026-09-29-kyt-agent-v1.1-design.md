# KYT Agent v1.1 設計文件：依 v1 eval 結果改進

- 日期：2026-09-29
- 狀態：設計已確認，待實作
- 前一版：[2026-09-25-kyt-agent-design.md](2026-09-25-kyt-agent-design.md)

## 1. 背景

v1 eval（20 筆，Gemini 3.8 Flash）的發現：

- 陽性案例的風險都在第 1 層，純規則在下限調為 HIGH 後即達 100% 召回，未測到 agent 追蹤間接曝險的能力
- 代幣轉帳只記錄 symbol，假冒的「ETH」代幣被當成真 ETH
- 報告引用模型自身的過時知識（稱 Tornado Cash 仍受制裁）
- 乾淨地址的 token 用量約為風險地址的 5 倍
- 31 次快照缺漏（約 10% 工具呼叫）

v1.1 不改架構，只在現有模組上擴充。

## 2. 假冒代幣與粉塵偵測

判斷由程式執行，LLM 只負責在報告中解釋。

### 2.1 資料

- `Transfer` 新增 `token_contract: LowerStr | None`；原生 ETH 與 internal 轉帳為 `None`
- 新增 `data/tokens.csv`：`contract,symbol,decimals,dust_threshold,source`，列出經查證的主流代幣（至少 USDT、USDC、DAI、WETH）
- 新增 `TokenRegistry`（`tokens.py`）：依合約查已知代幣、依 symbol 查正牌合約

### 2.2 標記規則

每筆轉帳由 `classify_transfer()` 打上以下旗標（可多個）：

| 旗標 | 條件 |
| ---- | ---- |
| `spoofed_token` | ERC-20 的 symbol 為 `ETH`；或 symbol 與已知代幣相同但合約不同 |
| `dust` | 原生 ETH 金額 < 0.0001；或已知代幣金額 < 該代幣的 `dust_threshold` |

- `get_counterparties` 的每個交易對手附上旗標統計，例如 `⚠ 偽冒代幣 7 筆、粉塵 1 筆`
- 帶 `spoofed_token` 的轉帳不計入總額
- 風險下限不受旗標影響：直接接觸制裁、混幣器、駭客地址仍為 HIGH（直接曝險一律人工審查，粉塵亦同）

## 3. 報告只根據工具事實

`INVESTIGATION_SYSTEM` 與 `REPORT_INSTRUCTION` 加入：

- 風險判斷只能依據工具結果與標籤庫，不得引用模型自身對實體的認知
- 標籤庫的分類為最終依據（例如 Tornado Cash 的分類為 `mixer`，不得稱為受制裁）
- 帶有 `spoofed_token` 或 `dust` 旗標的往來，須在 finding 中說明

## 4. 降低乾淨地址成本

- `CaseState` 新增 `calls_without_risk: int` 與 `wrap_up_hinted: bool`
- `tools` 節點每執行一次工具：若新登記的地址帶有 `sanctioned`、`hack`、`mixer`、`bridge` 標籤，歸零；否則 +1
- 當 `calls_without_risk >= WRAP_UP_HINT_AFTER`（預設 6）且尚未提示時，`tools` 節點在 ToolMessage 之後附加一則 HumanMessage：「已連續 N 次查詢未發現風險跡象，請評估現有證據是否足以結案」，並設 `wrap_up_hinted = True`
- 提示放在 ToolMessage 之後，不破壞 tool_call 與 ToolMessage 的配對
- 補查時重置 `calls_without_risk` 與 `wrap_up_hinted`
- 只是提示，不強制結束；硬性上限仍由既有預算控制

## 5. Eval 與錄製

### 5.1 資料集擴充（v1 的 20 筆保留）

| 類別 | 筆數 | 定義 |
| ---- | ---- | ---- |
| `indirect_exposure`（陽性） | 約 6 | 目標的直接交易對手 X 無標籤；X 最近轉入中，來自 `mixer` 或 `sanctioned` 地址的筆數超過一半；目標與 X 至少 2 筆往來或單筆非粉塵；目標的直接交易對手皆無風險標籤 |
| `indirect_minor`（困難陰性） | 約 4 | 結構相同，但 X 的風險轉入低於 10%（至少 1 筆） |

- 陽性的來源：Tornado Cash 池合約的提領對象（internal 轉帳）作為 X，再取 X 的轉出對象作為目標
- 所有地址須為 EOA、不在標籤庫、實際從鏈上查得，`source` 註明找法與日期
- 數量不足時照實記錄，不湊數
- `expected` 定義不變：是否應攔下人工審查（HIGH 以上）

### 5.2 快照

- `Transfer` 新增欄位後，舊快照缺少 `token_contract`，須全部重新錄製
- 爬蟲錄製範圍不變（目標周圍 2 層、目標層的範例交易），因為擴大到第 2 層合約資訊與各層範例交易，估計需要數萬次 API 呼叫
- 新增 `kyt eval --fill-missing`：eval 以 read-through 錄製模式執行，agent 實際查到的缺漏資料即時補錄並寫入快照，結果中回報補錄筆數
- 之後的 eval 仍以純重播執行；換模型時若出現新缺漏，再用 `--fill-missing` 補齊

### 5.3 其他

- eval 模式（`auto_approve`）不寫入 `var/cases`
- 地址改掛到較淺層時，其已登記的子孫節點深度一併更新
- eval 摘要新增：陽性依類別的召回率、乾淨地址的平均 token

## 6. 設定

| 設定 | 預設值 | 說明 |
| ---- | ------ | ---- |
| `WRAP_UP_HINT_AFTER` | 6 | 連續幾次工具呼叫未發現風險後提示收尾 |
| `NATIVE_DUST_THRESHOLD` | 0.0001 | 原生 ETH 粉塵門檻 |

## 7. 測試

- 單元：`classify_transfer`（偽冒 ETH、同 symbol 異合約、粉塵、正常）、`TokenRegistry`、工具輸出含旗標且偽冒金額不計入總額、收尾提示的觸發與重置、子孫深度更新、eval 模式不寫 `var/cases`、`--fill-missing` 的 read-through 行為
- 流程：fake model 走完含收尾提示的案件，確認提示位於 ToolMessage 之後
- 整合：重錄快照後以真實 Gemini 跑完整 30 筆 eval，與 v1 比較

## 8. 驗收

- 30 筆 eval 無錯誤，快照缺漏在 `--fill-missing` 後為 0
- 報告 `indirect_exposure` 的召回率、`indirect_minor` 與交易所用戶的誤報率，並與純規則對照
- 乾淨地址的平均 token 相較 v1 下降
- 假冒「ETH」代幣案例（`0x5d202dab`）的報告正確指出偽冒代幣
- 報告不再稱 Tornado Cash 受制裁

## 9. 修訂（2026-09-29，設計確認後追加）

### 9.1 交易證據短代號

v1 eval 的 token 分析顯示，約 70% 的上下文是工具結果，其中大量是 66 字元的交易 hash（每個約 35–40 token）。

- 工具輸出中的交易以 `T1`、`T2`… 代替 hash，由程式在案件內依首次出現順序配號，同一 hash 永遠對應同一代號
- `Evidence` 新增 `ref`：tx 證據的 `id` 為代號、`ref` 為真實 hash；label 證據維持 `label:<address>`、`ref` 為地址
- `get_transaction` 接受代號（也接受已登記的 hash）
- 報告 finding 引用代號；`finalize` 在證據驗證之後把代號換回真實 hash，存檔的報告、markdown 與 audit log 只出現真實 hash
- 地址維持完整形式，因為 LLM 需要以地址呼叫工具

### 9.2 間接曝險的風險等級

報告 prompt 的等級定義改為：

- HIGH：直接接觸制裁、駭客、混幣器資金；或經由中間地址間接接觸，且該中間地址的資金高度依賴混幣器或制裁來源（超過一半）
- MEDIUM：其餘的間接接觸高風險實體

此定義與 `indirect_exposure` 的 `expected: risky` 一致；規則下限仍只看第 1 層，間接曝險的判斷交由 agent。

### 9.3 Eval 執行次數

只執行一次完整 eval（`kyt eval --fill-missing`），其結果即為 v1.1 的 eval 數字；純重播的重現性驗證延後到換模型比較時進行。預估 LLM 費用約 $3.5。
